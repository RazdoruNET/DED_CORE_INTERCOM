# Протокол связи гарнитуры с сервером

Звук по Bluetooth **не ходит**: BLE используется только для первой привязки
([`05-pairing-security.md`](./05-pairing-security.md)), потому что его пропускной
способности не хватает даже на один аудиопоток в обе стороны и он не переживает
движение по трассе.

Транспорт — один долгоживущий **бинарный WebSocket** на устройство:
`wss://<api>/api/assistant/speaker/stream`. Устройство сначала устанавливает
проверенный TLS-канал, затем отправляет `HELLO` первым бинарным сообщением.
Ключ и одноразовый токен запрещено передавать в URL или HTTP-заголовках.
Сервер должен закрыть соединение, если корректный `HELLO` не пришёл за 5 секунд.

## Кадр

```
 0        1        2        3        4        5        6
+--------+--------+--------+--------+--------+--------+--------- - - -
|  type  | flags  |  streamId (u16 LE)  |  seq (u16 LE)   |  payload
+--------+--------+--------+--------+--------+--------+--------- - - -
```

* заголовок 6 байт, payload до 1200 байт (`MTU 1280` за вычетом TLS/WS);
* `streamId` различает параллельные потоки: ответ агента, интерком, подсказки;
  `0` — служебный;
* `seq` — счётчик внутри потока, по нему отбрасывается переупорядоченное и
  считается потеря кадров;
* `flags` — биты: `0x01` начало потока, `0x02` конец потока, `0x04` повтор,
  `0x08` mark (для VAD/прерывания).

JSON в payload — только для управляющих кадров, никогда для звука.

## Типы кадров

| Код | Имя | Направление | Payload |
|---|---|---|---|
| `0x01` | `HELLO` | ↑ | JSON: `device`, `product`, `fw`, `hw`, `volume`, `muted`, `codec`, `rate`, `pub`, `key`/`token` |
| `0x81` | `HELLO_ACK` | ↓ | JSON: пользователь, кодек, кадр, битрейт, голос, heartbeat |
| `0x02` | `MIC` | ↑ | PCM16-кадр микрофона (целевой Opus) |
| `0x03` | `SAY` | ↓ | PCM16-кадр речи агента (целевой Opus) |
| `0x04` | `SPEECH_BEGIN` | ↓ | JSON: `{streamId, text?}` |
| `0x05` | `SPEECH_END` | ↓ | JSON: `{streamId, truncated}` |
| `0x06` | `VAD` | ↑ | JSON: `{event: start\|end, rms, ms}` |
| `0x07` | `CONTROL` | ↕ | JSON: `stop`, `barge_in`, `ping`, `pong`, `ack` |
| `0x08` | `STATE` | ↑ | JSON: громкость, mute, RSSI, heap, uptime |
| `0x09` | `EVENT` | ↑ | JSON: `wake`, `button`, `timer`, `error` |
| `0x0A` | `CMD` | ↓ | JSON: `say`, `led`, `volume`, `intercom.start`, `intercom.end`, `ota` |
| `0x0B` | `CODEC` | ↓ | JSON: `{codec, rate, frameMs, bitrate}` |
| `0x0C` | `INTERCOM` | ↕ | PCM16-кадр разговора (целевой Opus) |

`CMD` с `intercom.start` переводит ленту в состояние разговора, `intercom.end`
возвращает в простой. Остальные команды гарнитуры — зажигание, карты — в этой
базе отсутствуют: их таблица пуста, прикладной слой появится отдельно
([`07-roadmap.md`](./07-roadmap.md)).

## Рукопожатие

```
гарнитура                              сервер
    │  HELLO {device, product, fw, hw,    │
    │         volume, muted, codec, rate,│  проверка ключа (хеш в базе)
    │         pub, key|token}             │
    ├─────────────────────────────────────►│  для токена: сверка pub
    │                                      │  с отпечатком привязки
    │  ◄──── HELLO_ACK {userId, voiceId,   │
    │         heartbeatSec, rulesVersion,  │
    │         serverTime}                  │
    │  ◄──── CODEC {opus, 16000, 20, 24000}│
    │  ◄──── CMD {rules.update} (если нужно)│
    │                                      │
    │  ◄════ SAY / CMD ════════════════════│  дальше только кадры
```

Если ключ не принят — `CONTROL {error: "unauthorized"}` и закрытие с кодом
`4401`. Повторная попытка не раньше чем через 30 с с backoff до 5 мин.
Сертификат сервера проверяется по CA, встроенному в локальный
`firmware/src/config/Secrets.h`; если CA отсутствует, соединение даже не
начинается. `ws://` и insecure TLS не поддерживаются.

`pub` — открытый ключ устройства (несжатая точка P-256, 130 hex). При входе по
одноразовому токену сервер сверяет `SHA-256(pub)` с отпечатком из записи
привязки и только потом выдаёт `deviceKey`: перехваченный BLE-кадр с токеном не
даёт чужому устройству стать этой гарнитурой.

`muted` — микрофон выключен. Пока он `true`, сервер не накапливает кадры `MIC`
и не запускает распознавание. Прошивка в этом состоянии кадры не шлёт вовсе, но
проверка на сервере остаётся: «микрофон выключен» — обещание пилоту, и оно не
должно зависеть от версии прошивки на устройстве. Переключение приходит событием
`EVENT {kind: muted|unmuted}`.

## Звук

**Сейчас в коде — PCM16, а не Opus.** `HELLO` отправляет
`codec: "pcm16"` и `rate: 16000`; микрофонный кадр — 640 байт (320 отсчётов
по 2 байта). Opus-энкодера и декодера в дереве нет, поэтому канал занимает
32 КБ/с в каждую сторону. Таблица ниже — целевые параметры, к которым перейдёт
кадр `MIC`/`SAY`; до этого бюджет задержки и экономия трафика остаются планом.

| Параметр | Значение | Почему |
|---|---|---|
| кодек | Opus, CELT+SILK, 16 кГц, моно | речь, декод на ESP32 ~15–20 МГц |
| кадр | 20 мс (320 сэмплов) | баланс задержки и накладных расходов |
| битрейт | 24 кбит/с вверх, 24 кбит/с вниз | 3 КБ/с вместо 32 КБ/с у PCM16 |
| сложность кодера | 0–2 | на 520 КБ SRAM и 240 МГц выше не имеет смысла |
| FEC | включён вниз, выключен вверх | потери вниз слышны, вверх — переспросим |

Сервер кодирует **тот же Opus для всех устройств** и кеширует результат по
`hash(фраза + голос + параметры кодека)`: у платформы уже есть кеш синтеза, к
нему добавляется вторая ступень «mp3 → opus». Один и тот же ответ синтезируется
один раз.

## Бюджет задержки (обращение → первый звук)

| Этап | Бюджет | Как достигается |
|---|---|---|
| VAD + end-of-speech | 500 мс | 400 мс тишины + подтверждение по энергии |
| подъём кадра до сервера | 50 мс | один WS, без новых соединений |
| STT (стриминговый) | 300 мс | партиалы sherpa-onnx, а не whisper на всю фразу |
| старт агента | 200 мс | по стабильному партиалу; быстрый разбор перехватывает команды |
| первый чанк TTS | 300 мс | `LiveSpeechStream` уже делит по фразам |
| mp3 → opus + дорога вниз | 150 мс | кеш + 2 кадра буфера |
| **итого** | **≤ 1.5 с** | |

В гонке этот бюджет жёстче, чем в комнате: на скорости 1.5 с — это десятки
метров трассы. Поэтому подтверждение приёма команды обязано приходить раньше
ответа агента: короткий сигнал и смена состояния ленты, а не ожидание полной
фразы.

Сейчас в платформе на этом пути 5–7 с: VAD 900 мс, whisper на всю фразу (~3 с
на четырёх ядрах), потом модель. Без стримингового STT гарнитура получится
«задумчивой» — это ограничение сервера, а не устройства.

## Barge-in и эхо

Аппаратное эхоподавление (AFE в esp-sr 2.x) требует S3+PSRAM, а PSRAM в рабочей
сборке выключена из-за сбоев Wi-Fi. Поэтому база работает в полудуплексе.
Сейчас действует только правило 3: пока гарнитура говорит, VAD не открывает
микрофонный поток, иначе сервер получает собственный голос агента. Остальное —
целевая схема, которая появится вместе с локальным распознаванием и AEC:

1. **слова-перебивки** (`стоп`, `замолчи`, `хватит`) распознаются локально даже
   во время речи; на них динамик глушится в ту же миллисекунду, поток
   закрывается кадром `CONTROL {barge_in}`, сервер снимает запуск;
2. **обращение во время речи** — то же самое: второй вопрос без «стоп»;
3. пока гарнитура говорит, обычный VAD **не** открывает микрофонный поток;
4. на S3 включается AFE с AEC, и правило 3 снимается — полный дуплекс. Это
   отдельный этап дорожной карты, а не текущее состояние.

Защита от самопрослушивания на сервере не нужна: полудуплекс исключает петлю
физически. В шлеме добавляется второй источник эха — корпус и стекло, поэтому
порог VAD и геометрия микрофона настраиваются под конкретное крепление.

## Устойчивость канала

* `ping` каждые 15 с, два пропущенных `pong` — реконнект;
* при потере 3 кадров подряд вниз поток прекращается, гарнитура просит
  `SPEECH_BEGIN` заново (сервер отдаёт с начала фразы, а не с начала ответа —
  буфер фразы живёт 60 с);
* при реконнекте `HELLO` несёт `lastStreamId`, незавершённый поток закрывается
  событием `SPEECH_END {truncated: true}`, и гарнитура не повторяет оборванную
  фразу;
* джиттер-буфер вниз — 3 кадра (60 мс); при недоборе играет тишину, а не рвёт
  звук;
* долгая потеря связи — сторожевой таймер перезагружает устройство, чтобы не
  остаться в нерабочем состоянии до конца заезда.

## Резервный путь по HTTP

Если WS не поднимается (мобильный прокси, слабый канал на трассе), гарнитура
работает урезанно, но работает:

| Метод | Ручка | Назначение |
|---|---|---|
| POST | `/api/assistant/speaker/{id}/utterance` | тело `audio/opus`, ответ `{text, streamId, replyOpusUrl}` |
| GET | `/api/assistant/speaker/{id}/speech/{streamId}/{n}` | готовый Opus-чанк, кешируется |

Этот путь удобен на этапе 1 прототипа: проще отладить тракт, когда ответ
приходит целиком.

## Коды ошибок

| Код | Смысл | Что делает гарнитура |
|---|---|---|
| `4401` | ключ не принят | не переподключается, лента красная, просит привязку |
| `4403` | устройство чужого пользователя | то же |
| `4426` | прошивка устарела (принудительно) | запускает OTA |
| `4503` | сервис перегружен | backoff 60 с, автономный режим |
| `4000` | обычное закрытие (сервер перезапустился) | реконнект через 2 с |

OTA-клиента в этой базе нет: код `4426` описан как часть контракта, но образ
обновляется вручную через USB.
