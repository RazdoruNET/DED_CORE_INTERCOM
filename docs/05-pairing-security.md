# Привязка гарнитуры и модель угроз

Самое опасное место во всём устройстве. Гарнитура — это микрофон на голове
пилота и, когда прикладной слой появится, орган управления машиной. Ошибка здесь
означает не «неудобно», а «чужой человек слушает пилота» и «чужой человек отдаёт
команды». Поэтому привязка строится на трёх независимых якорях доверия, а не на
одном.

## Что защищаем

| Что | Цена ошибки |
|---|---|
| пароль Wi-Fi | доступ в сеть пилота или бокса |
| право управлять гарнитурой голосом | подслушивание, посторонние команды |
| доступ к платформе от имени пользователя | личные данные, оплата, чужие устройства |
| сама гарнитура как имущество | кража и перепривязка к вору |
| голос пилота и его команды | запись разговоров, повтор команд в гонке |

## Модель угроз

| # | Атакующий | Что пытается |
|---|---|---|
| A | человек с телефоном в радиусе BLE на паддоке | привязать гарнитуру к своему аккаунту |
| B | пассивный перехватчик эфира | прочитать Wi-Fi пароль из BLE |
| C | подставное BLE-устройство | выдать себя за гарнитуру и получить Wi-Fi пароль сайта |
| D | подставной сайт или сервер | выдать себя за платформу и завладеть устройством |
| E | вор, укравший гарнитуру | привязать к себе, прочитать NVS |
| F | бывший член команды, знавший пароль Wi-Fi | вернуть себе доступ |
| G | запись голоса пилота | отдать команду зажигания или карт его голосом |

Угроза G пока ограничена: прикладной таблицы команд у гарнитуры нет, и
команда голосом не исполняется. Как только слой появится, защита от повтора
записи станет обязательной — см. [`07-roadmap.md`](./07-roadmap.md).

## Три якоря доверия

1. **Код на наклейке** — индивидуальный секрет устройства, печатается при
   производстве и хранится в базе платформы. Единственный признак физического
   владения.
2. **Ключ устройства P-256** — генерируется на первом включении и живёт в NVS.
   По нему гарнитура доказывает серверу, что она — это она, и по нему сайт
   шифрует настройки.
3. **Сервер** — единственная сторона, которая связывает код и устройство. Ни
   гарнитура, ни сайт не решают сами, чья это вещь.

Ни один из трёх не достаточен в одиночку: код можно сфотографировать, ключ можно
вычитать из флеша, сервер можно подменить. Вместе они закрывают всю таблицу.

## Поток привязки

```
пилот               сайт (Chrome/Edge)          сервер            гарнитура
     │   код с наклейки  │                        │                  │
     │  выбор устройства │                        │                  │
     │  в списке BLE     │                        │                  │
     │                   │ ──── BLE: info ───────────────────────────►│
     │                   │ ◄── {id, pub, challenge, frame, fw} ────────┤
     ├──────────────────►│  pair/claim {code, id, pub, challenge}    │
     │                   ├───────────────────────►│ создаёт pairToken│
     │                   │  ◄── {signed grant} ───┤ (10 мин, однораз.)│
     │                   │  проверяет grant, ECDH + HKDF + AES-GCM  │
     │                   │ ──── BLE: pair (кадр) ────────────────────►│
     │                   │ ◄─── {stage: paired} ─────────────────────┤
     │                   │                        │   ◄── HELLO {token, pub}
     │                   │                        ├── сверка pub и токена
     │                   │                        ├── token → deviceKey
     │                   │                        │   закрепление отпечатка
     │                   │                        │   ── HELLO_ACK ──►│
```

Пошагово:

1. Пилот: профиль → «ИИ Агент» → «Добавить устройство» → вводит 12 символов с
   наклейки либо сканирует QR `DED1:<deviceId>:<code>`. Код должен быть заранее
   создан и зарегистрирован сервером при производстве устройства.
2. Сайт открывает выбор BLE-устройства (`navigator.bluetooth.requestDevice` с
   фильтром **только по UUID сервиса**), пилот выбирает гарнитуру. Фильтровать
   по имени нельзя: 128-битный UUID съедает 18 из 31 байта рекламного пакета,
   имя обрезается, а macOS показывает закэшированное имя от прежней прошивки.
3. Сайт читает характеристику `info` (`deviceId`, открытый ключ и случайный
   128-битный challenge текущего окна) и отправляет их вместе с кодом:
   `POST /api/assistant/speaker/pair/claim {code, deviceId, publicKey, challenge}`.
   Имена ручек платформы общие для базы: гарнитура использует тот же контракт,
   что и колонка.
4. Сервер находит устройство по хешу производственного кода, проверяет, что оно
   свободно, создаёт одноразовый `pairToken` (TTL 10 минут) и возвращает grant.
5. Сервер подписывает grant ключом ES256, закрытый ключ хранится только на
   сервере в Vault. Подписываются строго канонические UTF-8 байты:

   ```
   DED-CORE-SPEAKER-PAIR-V1\n
   {deviceId}\n
   {lowercase hex SHA-256(devicePublicKey)}\n
   {challenge из BLE info}\n
   {userId}\n
   {pairToken}\n
   {apiBase}
   ```

   Домен подписи общий для базы — оба изделия используют один контракт.
   ECDSA-подпись передаётся как DER в стандартном Base64. Прошивка проверяет
   подпись по закреплённому `SPEAKER_PAIRING_PUBLIC_KEY_HEX` (несжатая точка
   P-256 в hex: в предсборке mbedTLS разбор PEM может быть выключен).
6. Сайт генерирует эфемерную пару P-256, считает ECDH с ключом гарнитуры и
   выводит ключ шифрования через HKDF. Кадр версии 1 выводит ключ из
   `HKDF(salt, ECDH, "ded-speaker-pair-v1")`, кадр версии 2 добавляет в
   `info` код с наклейки (`"ded-speaker-pair-v2"` + `\n` + код).
7. Сайт шифрует настройки AES-256-GCM и пишет кадр в характеристику `pair`.
   Гарнитура проверяет подпись grant, отпечаток собственного ключа и
   расшифровывает настройки. При ошибке настройки не применяются.
8. Гарнитура перезагружается и при первом WSS-подключении отправляет
   `HELLO {token, pub}`. Сервер сверяет `pub` с отпечатком привязки, меняет
   токен на `deviceKey` и только тогда закрепляет отпечаток.

## Почему это закрывает модель угроз

| Угроза | Что её закрывает |
|---|---|
| A | окно BLE открывается только удержанием кнопки 5 с; уже привязанное устройство не принимает повторную привязку |
| B | настройки в BLE не идут открытым текстом: ECDH + HKDF + AES-256-GCM |
| C | grant подписан сервером и привязан к `deviceId`, ключу и challenge; кадр версии 2 требует код с наклейки |
| D | гарнитура доверяет только CA платформы, `ws://` и insecure TLS не поддерживаются |
| E | без `deviceKey` устройство бесполезно; после сброса нужна новая привязка; в серии — flash encryption |
| F | токен одноразовый, отпечаток ключа закреплён; сброс стирает NVS и ключ |
| G | пока команды не исполняются; в будущем — подтверждение действия и привязка команды к активной сессии, а не к записи |

## Повторная привязка и продажа

| Событие | Что происходит |
|---|---|
| владелец меняет гарнитуру | «Отвязать» в профиле — сразу, без карантина |
| владелец продаёт гарнитуру | отвязывает сам, покупатель привязывает кодом с наклейки |
| гарнитура потеряна или украдена | владелец жмёт «Это не я» → блокировка, устройство не принимает команды |
| новый владелец без доступа к аккаунту | код с наклейки → карантин 7 дней + уведомление прежнему владельцу; молчание 7 дней = согласие |

Сброс кнопкой (удержание 10 с) стирает NVS и ключ. Сервер при следующем
подключении видит незнакомый ключ и **не** отдаёт данные — устройство просто
перестаёт работать до новой привязки. Прежний владелец получает уведомление
«гарнитура сброшена».

## Ограничения, о которых надо сказать вслух

* **Just Works в BLE.** Полноценное BLE-спаривание с числовым сравнением требует
  экрана, которого у гарнитуры нет. BLE-линк не считается доверенным:
  конфиденциальность даёт собственный ECDH, аутентичность — `pairToken` от
  сервера. MITM может помешать (DoS), а на **первой** привязке — подсунуть своё
  устройство вместо гарнитуры: от этого защищают короткое окно по кнопке, сверка
  `pub` при обмене токена и внимательность пилота при выборе устройства в списке.
* **Повтор кадра.** Записанный кадр привязки можно повторить, но окно закрыто
  после успеха, а `pairToken` внутри уже потрачен — сервер второй раз его не
  примет.
* **Наклейку можно сфотографировать.** Поэтому код 12 символов (≈60 бит), лимит
  попыток (5 в час на пользователя, 10 в час на код) и уведомление владельцу о
  каждой попытке привязки его устройства.
* **NVS на прототипе не шифрован.** Ключ устройства и пароль Wi-Fi можно
  вычитать, имея физический доступ и UART. На серийной плате обязательны flash
  encryption и secure boot — это отдельный пункт производства, не
  «когда-нибудь» ([`06-production-security.md`](./06-production-security.md)).
* **Web Bluetooth не работает в iOS Safari.** На iOS привязка идёт через
  мобильное приложение (Capacitor + BLE-плагин). Это ограничение платформы, а не
  наше; на сайте показываем «откройте приложение».

## Что нужно от сервера

Реализовано в `AssistantService` платформы; в публичном репозитории эти файлы не
публикуются — здесь описан контракт.

| Элемент | Где |
|---|---|
| `POST /api/assistant/speaker/pair/claim` | `SpeakerController` |
| `POST /api/assistant/speaker/{id}/unbind` | там же |
| `POST /api/assistant/speaker/{id}/report-stolen` | там же |
| таблица `SpeakerPairings` | `deviceId`, `codeHash`, `userId`, `tokenHash`, `createdAt`, `expiresAt`, `usedAt` |
| атомарный обмен токена на ключ | в `SpeakerGateway` при `HELLO`, один `UPDATE ... WHERE used_at IS NULL` |
| лимиты и аудит | `AssistantAuditEntries` + счётчик попыток по коду и по IP |

Код и токен хранятся **только хешами** (SHA-256 с солью устройства): утечка базы
не должна давать возможности привязать чужую гарнитуру.

## Текущее состояние реализации

Реализованы обе стороны: прошивка (ключ P-256, GATT-характеристики, обмен
зашифрованным кадром, проверка подписи grant, криптосамопроверка) и сервер
(`pair/claim`, `devices`, `unbind`, `report-stolen`, `rename`, обмен токена на
`deviceKey`, WebSocket `/api/assistant/speaker/stream`). Границы:

* окно BLE открывается только после удержания физической кнопки 5 секунд и
  живёт 5 минут; автоматической рекламы при старте нет (стендовые `*_bench`
  сборки — только для макета);
* уже сопряжённая гарнитура не принимает повторную привязку по BLE — сначала
  требуется отвязка в профиле на сайте;
* отпечаток ключа закрепляется при обмене токена на WSS, а не в момент claim:
  прерванная или подставная привязка не занимает устройство навсегда;
* соединение WSS требует доверенный CA из локального `config/Secrets.h`;
  без него прошивка отказывается от TLS, а не переходит в insecure-режим;
* пока не задан `SPEAKER_PAIRING_PUBLIC_KEY_HEX`, прошивка не принимает ни один
  кадр привязки — это безопасный отказ, а не временное отключение проверки;
* пока не задан доверенный CA, гарнитура не подключается к серверу вообще.

## Версии кадра привязки

Версию диктует гарнитура: она сообщает её полем `frame` в BLE `info`, и кадр
другой версии отвергает. Иначе подменяющее BLE-устройство могло бы «откатить»
схему к варианту без кода.

| Версия | Когда | Ключ кадра | Что защищает |
|---|---|---|---|
| 1 | код с наклейки в устройство не прошит (макет) | HKDF(salt, ECDH, `"ded-speaker-pair-v1"`) | только от пассивного перехвата |
| 2 | код прошит в NVS (`spk_id/code`) | HKDF(salt, ECDH, `"ded-speaker-pair-v2"`, `\n`, код) | и от подставного BLE-устройства |

Серийные устройства обязаны работать версией 2 — это пункт производства
([`06-production-security.md`](./06-production-security.md)). Формула вывода
ключа закреплена эталонными векторами в
[`../tools/pairing-kdf-check.py`](../tools/pairing-kdf-check.py): прошивка, сайт и
стендовый `pair.py` обязаны давать одинаковый ключ, иначе привязка ломается
«без причины».

## Остаточные риски

Их нужно назвать вслух — они не закрыты кодом, и в публичном репозитории о них
напишут первым делом.

* **Первая привязка на устройстве без кода (кадр версии 1) — TOFU.** Сервер
  впервые видит открытый ключ из BLE, когда человек вводит код с наклейки.
  Подставное BLE-устройство, выбранное в списке *вместо* настоящей гарнитуры,
  получит зашифрованный кадр и прочитает Wi-Fi пароль. На устройстве с прошитым
  кодом (версия 2) этого не происходит: ключ выводится с участием кода, которого
  у подставного устройства нет.
* **Код с наклейки** хранится на сервере как `SHA-256(deviceId:code)` без
  серверного «перца»: утечка базы позволяет офлайн-перебор, поэтому код обязан
  быть не короче 60 бит случайности.
* **NVS прототипа не шифрован**: ключ устройства, пароль Wi-Fi и код привязки
  читаются при физическом доступе к UART. Серийная сборка `esp32s3_prod`
  отказывается работать без flash encryption.
* **BLE-линк не аутентифицирован** (Just Works): MITM может мешать привязке
  (DoS), но не расшифровать кадр версии 2 и не подменить grant — подпись
  проверяется на устройстве.
* **Непрерывный захват.** Пока гарнитура на связи и микрофон не выключен, звук
  уходит на сервер непрерывно (VAD решает, что считать репликой). Выключение
  микрофона останавливает захват в прошивке и отбрасывается сервером, но
  «пауза прослушивания» должна быть видимой — красная лента перекрывает любое
  состояние.

## Проверено на железе

| Что | Результат |
|---|---|
| ключ P-256 создаётся и переживает перезагрузку | да, тот же открытый ключ после рестарта |
| самопроверка ECDH → HKDF → AES-GCM на устройстве | проходит (`[crypto] самопроверка привязки: ок`) |
| серверная подпись grant | проверена сквозным тестом независимой реализацией; подпись чужим ключом отвергается |
| шифрование кадра | ECDH → HKDF → AES-256-GCM: ключи на обеих сторонах совпали байт в байт |
| отказ при неверном challenge/ключе/адресе | отвергается до применения настроек |
| BLE-реклама с сервисом `6b1f0001-…` | видна сканером, `local_name = DED-SPK-<4 hex>` |
| окно привязки закрывается по таймауту | 5 минут, дальше устройство невидимо |

Имена рекламы и сервиса унаследованы от базы и одинаковы для обоих изделий.

## Что нужно от сайта

Модуль привязки в фронтенде (`/speaker/pair`):

1. ввод или скан кода → `pair/claim`;
2. `navigator.bluetooth.requestDevice({filters:[{services:[SERVICE_UUID]}],
   optionalServices:[SERVICE_UUID]})`;
3. чтение `info`, сверка ключа с серверным;
4. WebCrypto: `generateKey(ECDH P-256)` → `deriveBits` → `HKDF` → `AES-GCM`;
5. запись кадра частями, ожидание `notify` со `stage: "paired"`;
6. экран «Готово» с предложением назвать устройство.

Всё это — примерно 200 строк TypeScript и ни одной новой зависимости.
